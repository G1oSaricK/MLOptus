# 1. Цели проектируемой антифрод-системы в соответствии с ТЗ

- **Сроки и бюджет:**
  - MVP: 3 месяца
  - Готовый проект: 6 месяцев
  - Бюджет: 10 млн руб.

- **Защита клиентов:**
  - Менее 2 жертв в месяц
  - Убыток менее 500 тыс. руб. в месяц

- **Производительность системы:**
  - 50–400 транзакций в секунду

- **Ложные срабатывания:**
  - Не более 5% в месяц

- **Развёртывание:**
  - Облачная инфраструктура

- **Формат хранения данных:**
  - CSV-файлы (строка = одна транзакция)

- **Конфиденциальность:**
  - Обеспечить защиту данных истории клиента и его транзакций


# 2 Аргументированно выбрать метрику машинного обучения, оптимизация которой, на ваш взгляд, позволит достичь поставленных целей.

Жертвы мошенников < 2 чел. и убыток < 500 тыс. руб. в месяц

Данная цель решается оптимизацией **recall** (исключение **FN** - пропущенных мошенников).  
При этом возможно увеличение ложных срабатываний (**FP**), но они должны оставаться в рамках **≤ 5%**.

Выстроив правильный процесс обработки FP, можно найти оптимальный баланс:

## 1. Сегментация клиентов
- **LTV высокий** - риск потерять клиента дороже возможного фрода.
- **Новые клиенты** - стандартный или усиленный сценарий проверки.

## 2. Сегментация операций
- **Мелкий ежедневный платёж** (например, в кофейню) - почти без проверок.
- **Крупный перевод на новый счёт** - полный набор верификации.

## 3. Step-up аутентификация (светофор)
| Уровень риска | Действие |
|---------------|----------|
| 🟢 **Низкий** | Пропускаем |
| 🟡 **Средний** | Подтверждение (SMS, push) |
| 🔴 **Высокий** | Блокировка + звонок оператора |

# 3 Проанализировать особенности проекта с использованием, например, MISSION Canvas. Это позволит выделить специфику проекта и формализовать требования к нему, подобрать инструментарий и критерии оценки.

# Бенефициары (Beneficiaries)
- **Клиенты банка (розница, МСБ)** – не теряют деньги
- **Банк** – снижает операционные расходы на ручной фрод-мониторинг и chargeback

# Ценностные предложения (Value Propositions)
- **Для клиента:** деньги не украдут, но и честный платёж не заблокируют
- **Для банка:** предсказуемая защита за 10 млн руб без перерасхода
- **Для IT:** готовая ML-модель в облаке через 6 месяцев, без покупки серверов
- **Для безопасности:** автоматическое выявление новых схем без ручного прописывания правил

# Развёртывание (Deployment)
- **Облачная платформа:** Yandex Cloud / VK / SberCloud
- **Хранение истории:** CSV-файлы (строка = транзакция)
- **Формат выдачи:** REST API для core-банка (синхронный ответ < 50 мс)
- **Защита данных:** шифрование при передаче и хранении, ролевая модель доступа

# Ключевые активности (Key Activities)
| Этап | Активность |
|------|------------|
| Месяц 1–2 | Сбор и разметка исторических CSV, проектирование признаков |
| Месяц 3 | MVP-модель (градиентный бустинг) + API, запуск в теневом режиме |
| Месяц 4–5 | Донастройка порога под FPR ≤ 5%, оптимизация производительности |
| Месяц 6 | Продакшн-релиз, мониторинг, обучение службы безопасности |

# Ключевые ресурсы (Key Resources)
- **Данные:** исторические CSV транзакций за 6–12 месяцев с метками фрода (dataset)
- **Аналитики и тестировщики:** 1–2 человека для проверки модели и бизнес-плана
- **Команда ML:** 3–5 специалистов (дата-сайентист, ML-инженер)
- **Команда DevOps:** 1–3 инженера по облаку и CI/CD
- **Инфраструктура:** облачные GPU (обучение) + CPU-кластер (инференс)

# Ключевые партнёры (Key Partners)
- **Облачный провайдер (Yandex Cloud / VK)** – квоты, SLA, поддержка
- **Подразделение фрод-мониторинга банка** – разметка данных и валидация срабатываний

# Бюджет миссии / Затраты (Mission Budget/Cost)
**Итого: ~2,1–4,0 млн руб**

| Статья | Стоимость (млн руб) |
|--------|---------------------|
| Вычислительные мощности (обучение GPU, например NVIDIA A100, 100–200 часов) | 0,2–0,5 |
| Вычислительные мощности (инференс CPU-кластер на 400 т/с, 6 месяцев) | 1,0–1,5 |
| Хранение данных (CSV-история + логи + бэкапы, 6 мес) | 0,3–0,5 |
| Разметка данных (выполняют сотрудники банка — не учитываем ФОТ) | 0 |
| Сетевой трафик (API запросы, выгрузки, синхронизация) | 0,1–0,2 |
| ПО и лицензии (MLflow, мониторинг, KMS — если платные) | 0–0,3 |
| Резерв / непредвиденные (запас 20%) | 0,5–1,0 |

# Показатели достижения миссии (Mission Achievement Indicators)

| Категория | Показатель | Целевое значение |
|-----------|------------|------------------|
| **Защита клиентов** | Кол-во жертв / мес | < 2 чел |
| | Убыток клиентов / мес | < 500 тыс. руб |
| **Качество модели** | FPR (ложные блокировки) | ≤ 5% |
| | Recall (доля пойманных мошенников) | максимизировать (цель > 90%) |
| **Производительность** | RPS (транзакций/сек) | 50–400 т/с |
| | Латентность ответа | < 50 мс |
| **Соблюдение ТЗ** | MVP готов | к месяцу 3 |
| | Релиз в облаке | к месяцу 6 |
| | Бюджет | ≤ 10 млн руб |

Попытаться декомпозировать планируемую систему, определить ее основные функциональные части.

Определить задачи, решение которых необходимо для достижения поставленных целей с учетом проведенного анализа. Задачи рекомендуется формулировать по принципу S.M.A.R.T. На текущий момент, пока не конкретизированы детали антифрод-системы, они могут быть представлены в достаточно общем виде. Но они позволят сформировать некоторый roadmap по реализации проекта.

Создать GitHub-репозиторий для проекта и разместить в нем сформулированные задачи (~5 задач) на Kanban-доске в GitHub Projects со статусом «Новые». В дальнейшем, при реализации проекта, эти задачи будут конкретизироваться, дробиться, видоизменяться и выполняться. Их статус тоже будет изменяться, что позволит вам наглядно оценивать степень завершенности проекта.
